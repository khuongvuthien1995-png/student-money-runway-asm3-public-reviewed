# Student Money Runway peer-access guide

## Verified access and boundaries

Open https://student-money-runway-asm3-preview.vercel.app/login in a normal browser. The Vercel access screen is disabled for this exact project; anonymous real HTTPS and prior four-width login checks pass. Protected financial screens still require Supabase Auth. Public GitHub source is not needed for Part B and remains blocked by history privacy review.

The built-in email sender does not establish signup for arbitrary nonmember addresses. Existing dedicated A/B are unconfirmed; do not tell peers unrestricted registration works. Custom SMTP is PAUSED. Never share the confirmed personal main account or its financial records.

## Safe review choices

- Arrange a supervised end-user session on the student's computer, using an account with data the owner permits to be shown. The official brief pp.2-3 expressly permits arranging a peer-computer session when hosting/access is unavailable.
- Alternatively, the owner may later authorize a separate approved disposable reviewer account and data. Provide credentials privately through an agreed channel, not GitHub/README/screenshots. This account has not been provisioned or promised by this task.
- Revisit a custom provider only after separate authorization if broader signup is required. Do not bypass confirmation/JWT/RLS or make reviewers organization members solely for mail eligibility.

The owner should state permitted actions and whether saving/confirming disposable data is allowed. The current main account is **read-only**: no plan updates, purchase confirmation or deletion. Reviewers do not need Supabase dashboard/database or repository access.

## Reviewer journey

1. Obtain the actual application URL, owner permission, account/supervision arrangement and data-write boundaries privately.
2. Observe login/confirmation/error feedback without capturing passwords or session tokens.
3. Evaluate the six-screen navigation, form feedback, loading/error states, mobile/desktop layout, financial preview and history only within permissions. Do not generate transactions on personal data.
4. Collect at least five genuine annotated screenshots of the peer application, redact unrelated personal data, and connect each observation to an actionable recommendation. Do not use this project's mock screenshots as evidence for another application.
5. Provide at least three specific recommendations with affected action, user impact and a reproducible improvement/retest. Include purpose/target user, UI, functionality, end-user security, peer role and actual communication attempts/outcome.

Current three templates are pending URLs/access, 0/5 genuine images and 0/3 evidence-based recommendations each. Preserve named assessment copies privately. If a peer cannot arrange review, record actual outreach and reflection as required by brief p.3; never invent contact attempts or findings.
